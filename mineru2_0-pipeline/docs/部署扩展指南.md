## 1. 现状概述

### 硬件配置

| 资源 | 规格 | 备注 |
|------|------|------|
| GPU | 2 × NVIDIA RTX 4090 (48GB VRAM) | |
| CPU | 64 物理核 / 128 逻辑核（超线程） | 超线程对计算密集型负载增益有限 |
| 内存 | 视实际配置 | 每个 Worker 约需 4~8GB |

> **重要区分：** 128 是逻辑核心数（含超线程），物理核心仅 64 个。对于 MinerU 这类 CPU 计算密集型负载（PDF 渲染、图像处理、numpy/OpenCV 运算），**超线程仅提供约 20%~30% 的额外吞吐，远非翻倍**。因此系统的有效 CPU 算力约等于 **75~85 个"等效物理核"**，而非 128。

### 运行配置

| 参数 | 值 |
|------|------|
| `workers_per_device` | 10 |
| GPU 数量 | 2 |
| 总 Worker 数 | 20（10 × 2） |
| `pipeline_size` | 3（默认） |
| `io_workers` | 2（默认） |
| 任务分页 | 每 10 页切分为一个子任务 |

### 观测到的现象

| 指标 | 表现 |
|------|------|
| CPU 利用率 | 128 个逻辑核全部达到 100%，持续满载 |
| GPU 利用率 | 在 5%～95% 之间频繁波动 |
| GPU 显存 | 高位运行，存在 OOM 风险 |
| 瓶颈 | CPU 侧 |

### 结论

**CPU 是当前系统的首要性能瓶颈，显存是潜在的稳定性风险。**

- CPU 的 64 个物理核被 20 个 Worker（及其子进程）严重超额认购
- GPU 算力充裕但被"饿着"，大量时间在等待 CPU 完成前后处理
- 10 个 Worker 共享单块 48GB 显存，在推理密集阶段可能逼近上限

## 2. 架构分析：瓶颈在哪里

### 2.1 处理流程全景

MinerU 解析一个 PDF 的完整流程中，GPU 只负责几个模型推理环节（版面检测、OCR 识别、公式识别、表格识别），**大量的前处理和后处理全部在 CPU 上完成**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│                  单个任务的处理流程（10页 PDF 分片）                       │
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  [CPU] PDF预处理        pypdfium2 页面提取、pdfminer 分类                │
│    ↓                                                                     │
│  [CPU] PDF渲染为图片    pypdfium2 渲染 + PIL 转换（多进程，最吃CPU）      │
│    ↓                                                                     │
│  [CPU] 图像预处理       numpy 数组转换、OpenCV 颜色/裁剪/padding          │
│    ↓                                                                     │
│  [GPU] 模型推理         版面检测、OCR、公式识别、表格识别                  │
│    ↓                                    ← 需要 VRAM，多 Worker 共享显存  │
│  [CPU] 布局后处理       IoU 计算、重叠过滤、框合并                       │
│    ↓                                                                     │
│  [CPU] OCR后处理        透视变换、文本行合并、Span 处理                   │
│    ↓                                                                     │
│  [CPU] 结果输出         图片裁剪+JPEG编码、Markdown生成、PDF标注          │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘

时间占比（估算）：

  CPU前处理    GPU推理    CPU后处理
├────────────┤├────┤├──────────────┤
     ~40%       ~20%       ~40%
```

**关键发现：一个任务的处理过程中，约 80% 的时间花在 CPU 上，仅约 20% 在 GPU 上。**

### 2.2 各阶段 CPU 开销详解

#### 阶段 A：PDF 预处理（纯 CPU）

| 操作 | 使用的库 | 说明 |
|------|----------|------|
| PDF 页面提取/拆分 | pypdfium2 | 按指定页范围提取，内存中重写 PDF |
| PDF 类型分类 | pdfminer + pypdfium2 | 判断应使用 OCR 模式还是文本模式：提取文本、统计字符、计算图片覆盖率、检测无效字符 |

#### 阶段 B：PDF 渲染为图片（最重的 CPU 操作）

| 操作 | 使用的库 | 说明 |
|------|----------|------|
| 逐页渲染为位图 | pypdfium2 | 默认 DPI 200，单页最大 3500px，**计算量极大** |
| 位图转 PIL Image | PIL/Pillow | bitmap → PIL 对象转换 |
| **多进程并发渲染** | ProcessPoolExecutor | 每个 Worker 默认启动 4 个渲染子进程（由 `MINERU_PDF_RENDER_THREADS` 控制） |

> 这是**单项最大的 CPU 消耗者**。高分辨率 PDF 渲染是纯 CPU 运算，且每个 Worker 会开 4 个子进程并行渲染。

#### 阶段 C：图像预处理（CPU 密集，numpy/OpenCV）

| 操作 | 使用的库 | 说明 |
|------|----------|------|
| PIL → numpy 数组 | numpy | 每页图片转为大型 ndarray |
| 区域裁剪（表格/公式/文本） | numpy + PIL | 大量的 crop 操作 |
| RGB → BGR 颜色转换 | OpenCV | OCR 模型需要的颜色空间 |
| 图像 padding 对齐 | numpy | 创建大型全白数组，拷贝到对齐边界（stride=64） |
| 透视变换（旋转裁剪） | OpenCV | `cv2.getPerspectiveTransform` + `cv2.warpPerspective` |
| 对比度计算 | OpenCV + numpy | 灰度转换、均值/标准差计算 |

#### 阶段 D：GPU 模型推理（消耗显存）

| 模型 | 说明 | 估算显存占用 |
|------|------|:------------:|
| 版面检测 (Layout Detection) | YOLO 系列，检测文本/图片/表格/公式区域 | ~0.5~1GB |
| OCR 检测 | 文字区域定位 | ~0.3~0.5GB |
| OCR 识别 | 文字内容识别 | ~0.5~1GB |
| 公式检测 + 识别 | LaTeX 公式定位与提取 | ~0.5~1GB |
| 表格识别 | 有线表/无线表结构识别 | ~0.5~1GB |
| 图片方向分类 | 旋转矫正 | ~0.1~0.2GB |
| **推理激活/中间张量** | 随输入图片大小和 batch 变化 | ~0.5~2GB |
| **CUDA 上下文** | 每个进程独立占用 | ~0.3~0.5GB |

> **单个 Worker 的 GPU 显存占用约 3~7GB**（取决于加载了哪些模型、MinerU 的 VRAM 管理策略、以及当前正在推理的页面复杂度）。

#### 阶段 E：布局分析后处理（纯 CPU）

| 操作 | 说明 |
|------|------|
| IoU（交并比）计算 | 大量边界框两两比较 |
| 嵌套表格过滤 | 去除重叠/嵌套的检测结果 |
| 低置信度框移除 | 按阈值过滤 |
| Block/Span 预处理 | 脚注检测、框排序 |
| 跨页表格合并 | 处理跨越多页的表格 |

#### 阶段 F：OCR 后处理（CPU 密集）

| 操作 | 使用的库 | 说明 |
|------|----------|------|
| 旋转区域裁剪 | OpenCV | 对倾斜文本做透视变换裁剪 |
| 检测框合并/排序 | numpy | 文本框去重、排序、合并 |
| Alpha 通道处理 | OpenCV | 通道分离与合并 |
| Span/行合并 | - | 将字符级结果拼接为文本行和段落 |

#### 阶段 G：结果输出（CPU）

| 操作 | 使用的库 | 说明 |
|------|----------|------|
| 图片/表格裁剪 + JPEG 编码 | PIL | 从原图裁出区域并压缩为 JPEG |
| Bbox 标注 PDF | reportlab + pypdf | 在原 PDF 上绘制检测框（调试用） |
| Markdown 生成 | - | 将结构化 JSON 转为 Markdown 文本 |

### 2.3 物理核 vs 逻辑核：超线程的真相

当前机器是 64 物理核 / 128 逻辑核（Intel 超线程或 AMD SMT）。很多人误以为 128 逻辑核 = 128 个完整核心，但实际并非如此：

```
┌───────────────────────────────────────────────────────┐
│               超线程对不同负载的增益                     │
├───────────────────────────────────────────────────────┤
│                                                       │
│  I/O 密集型（网络/磁盘等待多）:  +40%~80% 增益        │
│  混合型（部分计算、部分等待）:    +20%~40% 增益        │
│  计算密集型（numpy/OpenCV/渲染）: +15%~25% 增益  ◀ MinerU │
│  高度优化的 SIMD 运算:           +0%~10% 增益         │
│                                                       │
└───────────────────────────────────────────────────────┘
```

**MinerU 的主要 CPU 负载（PDF 渲染 + numpy + OpenCV）属于计算密集型**，超线程增益仅约 20%。因此：

| 度量方式 | 核心数 | 说明 |
|----------|:------:|------|
| 逻辑核（htop 看到的） | 128 | 包含超线程 |
| 物理核（真实硬件核心） | 64 | 独立执行单元 |
| **等效计算能力**（对 MinerU） | **~75~80** | 64 × 1.2 ≈ 77，超线程仅提供约 20% 增益 |

> **这意味着：当 htop 显示 128 个逻辑核全部 100% 时，系统实际的有效算力只相当于约 75~80 个物理核满载，且由于超线程导致的资源争用（缓存、执行端口），每个线程的实际效率会低于独占物理核时的表现。**

### 2.4 进程/线程爆炸分析

以当前配置（20 个 Worker），系统中实际的并发计算单元远超表面看到的数字：

```
每个 Worker 进程内部结构：
┌─────────────────────────────────────┐
│  Worker 进程 (LitServe 独立进程)     │
├─────────────────────────────────────┤
│  • 1 × 主推理线程（GPU + CPU处理）   │
│  • 2 × I/O 线程（io_workers=2）     │
│  • 1 × 异步事件循环线程              │
│  • 4 × PDF渲染子进程                 │
│    (ProcessPoolExecutor, 默认4)      │
└─────────────────────────────────────┘
```

**20 个 Worker 的总并发量：**

| 组件 | 数量 | 说明 |
|------|------|------|
| Worker 主进程 | 20 | LitServe 为每个 Worker 创建独立进程 |
| 推理线程 | 20 | 每个 Worker 1 个，执行 GPU 推理 + CPU 前后处理 |
| I/O 线程 | 40 | 每个 Worker 2 个（`io_workers=2`） |
| 事件循环线程 | 20 | 每个 Worker 1 个异步循环 |
| PDF 渲染子进程 | **最多 80** | 每个 Worker 最多 4 个（`MINERU_PDF_RENDER_THREADS` 默认 4） |
| **总计** | **~180** | 远超 64 物理核（~75 等效核）的承载能力 |

> **180 个活跃计算单元争抢 64 个物理核心（~75 等效核），CPU 严重超额认购约 2.4 倍。** 大量时间浪费在上下文切换和超线程资源争用上。

### 2.5 GPU 利用率波动的原因

GPU 利用率在 5%～95% 之间频繁波动，根本原因是 **CPU 无法稳定地为 GPU 供给数据**：

```
理想情况（CPU 充裕）：
  Worker1: [CPU] → [GPU] → [CPU]
  Worker2:    [CPU] → [GPU] → [CPU]
  Worker3:       [CPU] → [GPU] → [CPU]
  GPU:      ████████████████████████████   ← 持续高利用率

实际情况（CPU 瓶颈）：
  Worker1: [====CPU排队====] → [GPU] → [====CPU排队====]
  Worker2: [====CPU排队====] → [GPU] → [====CPU排队====]
  GPU:     ██░░░░░░░░░██░░░░░░░██░░░░░   ← 断断续续
```

- **GPU 95%**：多个 Worker 碰巧同时完成 CPU 预处理，同时提交 GPU 推理
- **GPU 5%**：大部分 Worker 卡在 CPU 预处理或后处理阶段，GPU 无任务可做

CPU 满载导致每个 Worker 的 CPU 阶段耗时被拉长（因为要与其他 Worker 争抢 CPU），GPU 被间歇性"饿死"。

### 2.6 显存（VRAM）压力分析

每张 RTX 4090 有 48GB 显存，10 个 Worker 共享这 48GB。

#### 显存消耗的组成

```
单个 Worker 的显存占用：
┌──────────────────────────────────────────┐
│  CUDA 上下文开销          ~0.3~0.5 GB    │  ← 每个进程固定开销
│  模型权重                 ~2~5 GB        │  ← 取决于 VRAM 管理策略
│  推理中间张量/激活        ~0.5~2 GB      │  ← 取决于页面复杂度
│  PyTorch 缓存             ~0.5~1 GB      │  ← CUDA 内存分配器预留
├──────────────────────────────────────────┤
│  单 Worker 总计           ~3.3~8.5 GB    │
└──────────────────────────────────────────┘
```

#### 多 Worker 共享显存的风险

| 每 GPU Worker 数 | 最低显存需求 | 峰值显存需求 | 48GB 是否安全 |
|:----------------:|:----------:|:----------:|:------------:|
| 4 | ~13 GB | ~34 GB | 安全 |
| 6 | ~20 GB | ~51 GB | 基本安全，峰值需注意 |
| 8 | ~26 GB | ~68 GB | 有风险 |
| **10（当前）** | **~33 GB** | **~85 GB** | **高风险，可能 OOM** |
| 12 | ~40 GB | ~102 GB | 极高风险 |

> **注意：** MinerU 内部有显存管理机制（`ModelSingleton` 模式复用模型、`MINERU_VIRTUAL_VRAM_SIZE` 控制加载策略、`clean_memory()` 定期清理）。实际显存占用取决于 MinerU 的策略——当检测到显存不足时，可能动态卸载部分模型到 CPU 或减少同时加载的模型数量。但这会**增加模型加载/卸载的开销**，间接降低 GPU 利用率。

#### 为什么目前没有频繁 OOM？

1. **不是所有 Worker 同时做 GPU 推理**：由于 CPU 是瓶颈，大部分 Worker 在等 CPU，同一时刻只有少数 Worker 在使用 GPU
2. **MinerU 的 VRAM 管理**：会根据 `MINERU_VIRTUAL_VRAM_SIZE` 动态调整加载策略
3. **任务分页（10 页/任务）**：限制了单次推理的输入规模，降低了峰值显存占用

但这种"靠 CPU 瓶颈间接保护显存"的平衡是脆弱的——**一旦加了 CPU 让更多 Worker 同时进入 GPU 推理阶段，显存 OOM 的风险会立即暴露**。

## 3. 任务分页策略分析

当前采用 **每 10 页切分为一个子任务** 的策略（例如 12 页 PDF → 10 页 + 2 页两个子任务）。

### 分页对各资源的影响

| 分页大小 | CPU 影响 | GPU 显存影响 | 吞吐量影响 | 延迟影响 |
|:--------:|----------|-------------|-----------|----------|
| 5 页 | 更多任务 → 更多调度开销 | 峰值更低，更安全 | 因调度开销略降 | 小文件更快完成 |
| **10 页（当前）** | **适中** | **适中，基本可控** | **均衡** | **均衡** |
| 20 页 | 更少任务 → 调度开销小 | 峰值更高，更危险 | 略高 | 大文件需等更久 |
| 不分页 | 最少调度开销 | 不可控，极易 OOM | 取决于 PDF 大小 | 大文件延迟极高 |

### 为什么 10 页是合理的选择

1. **显存可控**：10 页的推理批次不会产生过大的中间张量
2. **任务粒度适中**：切得太碎会增加调度开销（数据库读写、文件 I/O）；太大则单任务长时间占据 Worker
3. **利于多 Worker 并行**：一个 100 页的 PDF 被拆成 10 个任务，可以分配给不同 Worker 并行处理
4. **跨页表格的平衡**：分页边界可能切断跨页表格，10 页的粒度在大多数场景下可以覆盖完整表格

### 分页大小的调优建议

| 场景 | 建议分页大小 | 原因 |
|------|:----------:|------|
| 显存紧张（Worker 多，GPU 少） | 5~8 页 | 降低峰值显存 |
| **一般场景（当前）** | **10 页** | **均衡** |
| 显存充裕（Worker 少，GPU 大） | 15~20 页 | 减少调度开销 |
| 以低延迟为优先 | 5 页 | 小任务快速完成 |

## 4. 优化方案一：参数调优（不改硬件）

### 4.1 降低 workers_per_device

**这是最有效的参数调优手段。**

当前 10 个 Worker/GPU 导致 CPU 过载和显存压力。降低 Worker 数可以：
- 减少 CPU 争抢，每个 Worker 获得更多 CPU 时间片
- CPU 前处理更快完成，GPU 等待时间缩短
- 降低显存压力，减少 OOM 风险
- GPU 利用率反而更稳定（虽然 Worker 少了，但每个 Worker 喂数据更快）

**调整方式（`docker-compose.yml`）：**

```yaml
environment:
  - WORKERS_PER_DEVICE=5    # 从 10 降到 5
```

**或命令行：**

```bash
python start_all.py --workers-per-device 5
```

**推荐值（64 物理核 CPU + 2 × 4090 48GB）：**

| workers_per_device | 总 Worker | 预估峰值进程数 | 等效核需求 | 显存安全 | 评估 |
|:------------------:|:---------:|:-------------:|:---------:|:--------:|------|
| 3 | 6 | ~42 | ~42 | 非常安全 | 太保守，GPU 吃不饱 |
| **4** | **8** | **~56** | **~56** | **安全** | **保守推荐** |
| **5** | **10** | **~70** | **~70** | **基本安全** | **均衡推荐** |
| 6 | 12 | ~84 | ~84 | 需要注意 | 激进，接近物理核上限 |
| 8 | 16 | ~112 | ~112 | 有风险 | 超出物理核，依赖超线程 |
| 10（当前） | 20 | ~140 | ~140 | 高风险 | 严重超载 |

> **基于 64 物理核 / ~75 等效核的实际算力，`workers_per_device=4~5` 是当前硬件的合理范围。**

### 4.2 控制 PDF 渲染并发数

每个 Worker 内部的 PDF 渲染默认使用 4 个子进程，这是 CPU 开销的最大来源之一。

**通过环境变量限制渲染进程数：**

```yaml
environment:
  - MINERU_PDF_RENDER_THREADS=2   # 从默认 4 降到 2
```

降低后的影响：
- 单个 10 页任务的渲染速度稍慢（从 4 路并行降为 2 路，但 10 页本身不多，影响有限）
- 总并发进程数大幅下降
- CPU 争抢减少，整体吞吐量可能反升

**不同配置的渲染进程总数对比：**

| workers_per_device | MINERU_PDF_RENDER_THREADS | 渲染进程总数 | 对 64 物理核的压力 |
|:------------------:|:-------------------------:|:------------:|:-----------------:|
| 10（当前） | 4（默认） | 80 | 严重过载 |
| 10 | 2 | 40 | 仍然过载（加上其他线程） |
| 5 | 4 | 40 | 中等 |
| **5** | **2** | **20** | **合理** |
| **4** | **3** | **24** | **合理** |

> 由于任务已按 10 页分片，每次渲染页数不多，`MINERU_PDF_RENDER_THREADS=2` 即可在合理时间内完成单任务的渲染。

### 4.3 调整 Pipeline 队列大小

`pipeline_size` 控制每个 Worker 可以同时缓冲多少个任务（默认 3）。

```bash
python litserve_worker.py --pipeline-size 2
```

- 降到 2：减少内存和显存压力，减少并发的 CPU 预处理任务
- 升到 5：增加预取，GPU 可能更少等待（但需要更多 CPU 和内存）

在 CPU 瓶颈且显存紧张的情况下，**建议维持默认值 3 或降到 2**。增大会同时加重 CPU 和显存负担。

### 4.4 调整 I/O 线程数

`io_workers` 控制每个 Worker 的 I/O 线程池大小（默认 2）。

```bash
python litserve_worker.py --io-workers 1
```

I/O 线程主要用于文件读写，CPU 开销不大，但线程数过多时上下文切换有开销。在 CPU 已满载的情况下，可以从 2 降到 1。

### 4.5 控制单 Worker 显存用量

MinerU 通过 `MINERU_VIRTUAL_VRAM_SIZE` 环境变量决定加载多少模型到 GPU。**默认情况下每个 Worker 进程会读取 GPU 总显存（48GB），但它不知道有其他 Worker 在共享同一块 GPU。**

**建议显式设置每个 Worker 可用的显存上限：**

```yaml
environment:
  # 48GB / workers_per_device，留一些余量给 CUDA 上下文和碎片
  - MINERU_VIRTUAL_VRAM_SIZE=8    # 5 workers/GPU 时: 48/5 ≈ 9.6，留余量设 8
```

| workers_per_device | 建议 MINERU_VIRTUAL_VRAM_SIZE | 说明 |
|:------------------:|:----------------------------:|------|
| 4 | 10 | 48/4=12，留余量设 10 |
| **5** | **8** | **48/5≈9.6，留余量设 8** |
| 6 | 6 | 48/6=8，留余量设 6 |
| 8 | 5 | 48/8=6，留余量设 5 |
| 10（当前） | 4 | 48/10≈4.8，空间非常紧张 |

> 设置较小的 `MINERU_VIRTUAL_VRAM_SIZE` 后，MinerU 会自动调整模型加载策略（可能将部分不常用的模型放在 CPU 端、或按需动态加载/卸载），以适配可用显存。这会略微增加模型切换的延迟，但能显著降低 OOM 风险。

## 5. 优化方案二：扩展硬件资源

### 5.1 增加 CPU 资源

增加 CPU 物理核心数是解除当前瓶颈最直接的方式。

> **重要：以下所有 CPU 核心数均指物理核，不含超线程。** 配比计算应基于物理核心数。

**经验法则：**

```
所需物理核 ≈ GPU数 × workers_per_device × (MINERU_PDF_RENDER_THREADS + 2)
```

其中 `+2` 涵盖 Worker 主线程的 CPU 前后处理和其他辅助线程的开销。

**扩展推荐（保持 2 × 4090）：**

| 物理核 | 逻辑核 | 可支撑 workers_per_device | 总 Worker | 预期效果 |
|:------:|:------:|:-------------------------:|:---------:|----------|
| 64（当前） | 128 | 4~5 | 8~10 | 物理核接近满载 |
| 96 | 192 | 6~8 | 12~16 | CPU 有余量，GPU 利用率改善 |
| **128** | **256** | **10~12** | **20~24** | **CPU 充裕，GPU 充分利用** |

按当前 2 块 GPU、每 GPU 10 Worker 的期望配置：
- 最低需要：20 × (2+2) = **80 物理核**
- 推荐配置：20 × (3+2) = **100 物理核**
- 理想配置：**128 物理核**（256 逻辑核）

### 5.2 增加 GPU 卡

增加 GPU 可以提升推理吞吐量，但**必须同时满足 CPU 和显存两个约束**。

#### 约束一：CPU 必须跟上

| GPU 数量 | workers_per_device | 总 Worker | 需要的物理核 | 当前 64 核够用？ |
|:--------:|:-----------------:|:---------:|:----------:|:---------------:|
| 2（当前） | 10 | 20 | ~80-100 | 不够 |
| 2 | 5 | 10 | ~40-50 | 够用 |
| 4 | 5 | 20 | ~80-100 | 不够 |
| 4 | 3 | 12 | ~48-60 | 勉强 |
| 8 | 3 | 24 | ~96-120 | 远不够 |

> 每增加一块 GPU 并保持相同的 workers_per_device，CPU 需求线性增长。

#### 约束二：显存必须够用

增加 GPU 卡的一个额外好处：**可以降低每 GPU 的 Worker 数，从而同时缓解 CPU 和显存压力**。

| 配置 | 总 Worker | 每 GPU Worker | 每 Worker 可用显存 | 需要物理核 |
|------|:---------:|:------------:|:----------------:|:---------:|
| 2 GPU × 10 workers | 20 | 10 | ~4.8 GB | ~80-100 |

| 4 GPU × 3 workers | 12 | 3 | ~16 GB | ~48-60 |
| 8 GPU × 3 workers | 24 | 3 | ~16 GB | ~96-120 |

> 4 GPU × 5 workers 与 2 GPU × 10 workers 总 Worker 数相同，但每 Worker 可用显存翻倍，模型加载更完整，推理更高效。

根据不同的业务增长需求，推荐以下渐进式扩展路径：

#### 路线 A：先加 CPU，充分利用现有 GPU

**成本最低，效果最直接。** 解决当前"GPU 被饿死"的核心问题。

          workers_per_device = 10 → CPU 严重过载，GPU 利用率不稳定
    ↓

    ↓

          workers_per_device = 10, render_threads = 3
          充分利用两块 4090
          预期吞吐提升: ~80%~120%（相对调参后的方案B）
```

适合场景：预算有限，希望先榨干现有 GPU 算力。

#### 路线 B：增加 GPU，同步增加 CPU

**吞吐量大幅增长，适合持续增长的需求。**

```
当前状态: 64 物理核 + 2 × 4090
    ↓
第一步:   128 物理核 + 4 × 4090

    ↓
第二步:   256 物理核 + 8 × 4090
          workers_per_device = 5, render_threads = 2
          MINERU_VIRTUAL_VRAM_SIZE = 8
          预期吞吐提升: ~500%+
```

> **关键原则**：每增加 1 块 GPU，需同步增加约 20~30 个物理核。

适合场景：需要大规模提升处理能力，且预算允许。

#### 路线 C：多机分布式部署

**突破单机瓶颈。**

```

    ↓

          - 64~128 物理核 CPU
          - 2~4 × 4090

          - 共享任务数据库 (需将 SQLite 替换为 PostgreSQL/MySQL)

**多机部署时各节点的推荐配置：**

| 节点类型 | 物理核 | GPU | workers_per_device | 每节点吞吐 | 成本效益 |
|----------|:------:|:---:|:-----------------:|:---------:|:--------:|
| 轻量节点 | 64 | 2 × 4090 | 5 | 基准 | 高 |
| **标准节点** | **128** | **4 × 4090** | **5** | **~2.5×** | **最优** |
| 高性能节点 | 256 | 8 × 4090 | 5 | ~5× | 中 |

## 7. 常见问题

### Q: 为什么减少 Worker 数反而可能提升总吞吐量？

A: 当 CPU 过载时，所有 Worker 都在争抢 CPU 资源，每个 Worker 的处理速度都被拖慢。减少 Worker 数后，每个 Worker 获得更多 CPU 时间，单个任务处理更快，GPU 等待时间缩短。总效果是：**少量快速 Worker 的吞吐量 > 大量慢速 Worker 的吞吐量**。

### Q: 128 逻辑核不等于 128 物理核？

A: 是的。超线程（Intel HT / AMD SMT）让每个物理核可以同时执行两个线程，操作系统看到 128 个"核心"。但两个超线程共享同一个物理核的执行资源（ALU、缓存等）。对于 MinerU 这种 CPU 计算密集型负载，超线程的增益仅 15%~25%，而非 100%。所以 64 物理核 + 超线程 ≈ **75~80 个等效核**的算力，而非 128 个。

### Q: PDF 渲染为什么这么吃 CPU？

A: PDF 渲染本质上是把矢量图形（文字、图形、嵌入图片）光栅化为位图。对于复杂的 PDF（大量矢量图、高分辨率图片、复杂排版），每一页的渲染都相当于"画"一张高分辨率图片，这是纯粹的 CPU 计算密集型操作。MinerU 默认以 DPI 200 渲染，单页可达数百万像素。

### Q: 能不能用 GPU 加速 PDF 渲染？

A: 目前 pypdfium2（基于 Chrome 的 PDFium）不支持 GPU 加速渲染。这是一个行业性限制，主流 PDF 渲染库（PyMuPDF、pypdfium2、Poppler）都是纯 CPU 实现。

### Q: MINERU_PDF_RENDER_THREADS 设成 1 会怎样？

A: PDF 渲染变为单线程串行，单个任务的渲染速度会下降。但由于任务已按 10 页分片，页数不多，影响比处理整个大文档时要小。在 CPU 极度紧张时可以考虑设为 1，但一般推荐至少设为 2。

### Q: 为什么加了 CPU 后可能出现显存 OOM？

A: 当 CPU 是瓶颈时，大部分 Worker 在排队等 CPU，同一时刻只有少数 Worker 在做 GPU 推理。这无意中"保护"了显存。一旦 CPU 充裕了，多个 Worker 可以同时进入 GPU 推理阶段，峰值显存用量会飙升。因此**加 CPU 的同时必须设置合理的 `MINERU_VIRTUAL_VRAM_SIZE`**。

### Q: 内存（RAM，非显存）需要注意什么？

A: 每个 Worker 进程需要加载模型的 CPU 端参数、PDF 渲染产生的大尺寸图片数组、numpy/OpenCV 的中间结果。建议每个 Worker 至少预留 4~8GB 系统内存。20 个 Worker 可能需要 80~160GB RAM。如果观察到内存不足或 swap 使用，优先降低 Worker 数。

### Q: 10 页分片会不会影响跨页表格的识别？

A: MinerU 内置了跨页表格合并机制（`cross_page_table_merge`），可以在后处理阶段将分片边界处被切断的表格重新拼接。10 页的分片粒度在大多数场景下可以覆盖完整表格，但对于极端情况（表格跨越超过 10 页）可能需要调大分页。
